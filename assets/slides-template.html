Part One

The Problem

Why great codebases stay unexplained

Let's start with the problem. Every engineering team I've spoken to has the same frustration — there's a gap between building something and being able to explain it to anyone who wasn't there when it was built.

Built it. Can't explain it.

The builder

Understands every file, every decision, every tradeoff

Everyone else

Sees a wall of code with no entry point

The cost

Onboarding slows. Knowledge silos form. AI gets stuck.

🧠→📦

Knowledge locked inside one person's head doesn't scale

The builder has all the context — why Redis was chosen over Postgres, why the auth layer sits between the API and the database, why the state machine was built that way. But that context lives entirely in their head. Everyone else who touches the codebase starts from zero. This is the problem we're solving.

The participant handout is intentionally sparse: concept summaries, key vocabulary, and blank space for writing. It converts to a Word doc via pandoc so it's printable.

Part Three

How It Works

Under the hood of the skill

Now let's look under the hood. I want to show you the four phases the skill runs through, the key files involved, and the design system that makes every output look the way it does.

Four Phases

01
Analyze

Read all key files, trace data flows, map the cast of characters and how they communicate

02
Design

Choose 4–6 modules (or slide sections), write the teaching arc, select interactive elements

03
Build

Write module HTML files with real code snippets, translations, animations, and quizzes

04
Assemble

Run build.sh — concatenates all parts into a single index.html, ready to open

The skill runs four phases. Phase 1 is pure reading — Claude works through the codebase to understand what it does and how it fits together. Phase 2 designs the curriculum. Phase 3 writes the content module by module, which is where the quality comes from — each module is independent and can be written by a separate agent in parallel. Phase 4 runs build.sh to assemble everything into one file.

The File Structure

codebase-to-anything/ ├── SKILL.md # brain ├── assets/ │ ├── _base.html # shell │ ├── styles.css # design system │ └── slides-template.html ├── references/ │ ├── content-philosophy.md │ ├── design-system.md │ └── interactive-elements.md └── scripts/ ├── main.js # JS engine └── build.sh # assembler
SKILL.md

The instruction set Claude reads. Defines all three format paths.

references/

Rules docs for content, design tokens, interactive element patterns.

main.js + build.sh

Copied verbatim into every course — never regenerated.

The skill is itself a codebase. SKILL.md is the brain — it defines all three format paths and the rules for each phase. The references folder contains the detailed specs Claude reads as it builds: design tokens, content philosophy, interactive element HTML patterns. And main.js plus build.sh are always copied verbatim — Claude never rewrites them, which keeps the output consistent.

The Design System

Warm off-white background

#FAF7F2 — like aged paper, never cold white

Bold accent color

One per course — vermillion, teal, amber, forest

Dark code blocks

#1E1E2E with Catppuccin syntax colors

Typography trio

Bricolage Grotesque — headings

DM Sans — body text

JetBrains Mono — code

One CSS variable re-themes everything

Change --color-accent and the entire course updates

The design system is opinionated by design. Warm off-white backgrounds instead of cold white — it reads like a well-designed notebook, not a generic SaaS app. One bold accent color, chosen to fit the project's personality. The typography trio is fixed: Bricolage Grotesque for headings, DM Sans for body text, JetBrains Mono for code. And the whole thing is driven by CSS custom properties — change the accent variable and every output re-themes automatically.

Three Things to Remember

Point it at any codebase

Local folder, GitHub URL, or the current project — the skill reads it and figures out what it does

Pick the format for your audience

Course for self-paced learners · Slides for stakeholders · Workshop for live sessions

Everything runs in the browser

No dependencies, no build step, no hosting — open the file and you're done

Three things. First: it works on anything — any repo, any language, any complexity level. Second: the format choice is an audience decision, not a technical one. Ask yourself who you're trying to reach and how they'll consume it. Third: all three outputs are self-contained HTML — no frameworks, no build pipelines, no hosting required. You open a file in a browser and it works.
